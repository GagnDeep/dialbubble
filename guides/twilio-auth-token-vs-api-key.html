Twilio Auth Token vs API Key: which to use

Use API keys for anything running in production, and keep the Auth Token for local testing and the few jobs that require it. A key can be limited and revoked on its own, while the Auth Token is one master credential that everything shares.

What is the difference between a Twilio Auth Token and an API key?

Both let a program sign in to Twilio's REST API using HTTP Basic authentication. The difference is how much each one can do and what happens when you have to replace it. Twilio's API keys overview calls keys the preferred way to authenticate.

 Auth TokenAPI key
UsernameAccount SID (starts AC)Key SID (starts SK)
PasswordAuth TokenKey secret
How manyOne primary, plus an optional secondary during rotationAs many as you create
AccessEverything on the accountDepends on key type
Can you view it again?Yes, in the ConsoleNo, the secret is shown once
Replacing itAffects everything using the tokenAffects only what uses that key

Here's the same request with each one. Only the login changes, which is why switching usually takes minutes.

What are Main, Standard and Restricted API keys?

Twilio has three types, listed in its Console guide to keys. Start with the narrowest one that does the job.

TypeWhat it can reachGood for
MainAll API resources, the same as Account SID and Auth TokenTools that manage accounts or other keys
StandardAll resources except Accounts and KeysMost apps that send texts and place calls
RestrictedOnly the permissions you tickA service with one job, such as sending messages

Twilio's docs say Main keys can be created only in the Console, and Restricted keys are available only in the United States region in the legacy Console flow. Keys are also region-specific, so a key made for one region won't sign in to another.

Why do they fail differently when one leaks?

This is the real reason to care. Imagine your credential ends up in a public code repository.

  • Leaked Auth Token: whoever finds it has full access to the account. To shut them out, you need to rotate the token, and everything using it must be updated before you promote the new one. See the steps for changing your Auth Token safely.
  • Leaked Standard or Restricted key: the finder gets only what that key allows. You revoke that one key, make a replacement for that one app, and nothing else is touched.

A key still spends your money

A Standard key can send texts and place calls, so a leak can still cost you. Treat every secret as sensitive, keep it out of source code, and check your usage logs after any leak.

A worked example: one account, three programs

Say you run a small shop with three things talking to Twilio:

ProgramCredentialWhy
Website order-confirmation textsRestricted keyIt only has to send messages
Staff call-back scriptStandard keyIt places calls and reads numbers and logs
Webhook signature checkAuth TokenTwilio signs webhooks with it, and no key can replace it

Now the call-back script's server gets compromised. You revoke its key and issue a new one. The website keeps sending and webhooks keep validating. Had all three shared the Auth Token, you'd be updating all three at once while the attacker still had full access to the account.

When do you still need the Auth Token?

API keys don't replace the token everywhere. You'll need it for:

  • Webhook validation. Twilio signs each webhook request using your Auth Token as the key. Rotating the token means updating your validation code too.
  • Rotating the token itself. Twilio's authentication guide shows the promotion and secondary token endpoints using Account SID and Auth Token.
  • Account and subaccount management. Those examples use the Account SID and Auth Token too. A Main key is the alternative, but a Standard key can't reach them.
  • Any API whose reference asks for it. Twilio's rule is to use keys unless a specific page says otherwise.

How do I move from an Auth Token to an API key?

  1. In the Console, open the API keys and tokens page under your account settings, and choose your region.
  2. Create a key, name it after the app that will use it, and pick Standard or Restricted.
  3. Copy the secret right away. Twilio shows it only once.
  4. Change your app to use the key SID and secret, and keep the Account SID in your request URL.
  5. Deploy, then make a real test request. A rejected login returns error 20003.
  6. If the old token was widely shared, rotate it now, so old copies stop working. Update webhook validation at the same time.

You can check you copied a key correctly using the credentials format checker, which never sends what you type anywhere.

Using a phone app rather than your own code? The same logic applies. Dialbubble accepts either your Auth Token or a Standard API key. A Standard key is a sensible choice because you can revoke that one phone without disturbing anything else. Restricted keys aren't the right fit, since the app needs broad access. Read how Dialbubble stores them on the security page.

Questions about Twilio API keys

Is a Twilio API key more secure than an Auth Token?
A key isn't stronger as a password, but it limits the damage. You can give each app its own key, restrict what it can do, and revoke it alone. An Auth Token is a single credential with full access that everything shares.
Which should I use for a quick local test?
The Auth Token is fine for testing on your own machine, and Twilio's own code samples say so. Twilio recommends API keys for production, so switch before you ship.
Can a Standard API key create more API keys?
No. Standard keys can't reach the Accounts or Keys resources. If a job truly needs those, it needs a Main key or the Account SID and Auth Token.
Does an API key work without the Account SID?
You still need the Account SID. It appears in the request URL and helper libraries ask for it alongside the key SID and secret. The key replaces the Auth Token, not the account identifier.
